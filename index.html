    02 — Work

    What I build

    One harness, six layers. Each layer is made of plain files in a single git repository, so the coding agent on top can be replaced. Select a block to see what is inside.

    01 · Agents

    Interchangeable agents

    The harness is designed to run with any provider, whatever the model. No logic lives in a tool-specific folder.

    • CLAUDE.md holds one import line that points to AGENTS.md.
    • .claude/ and .agents/ hold one-line pointers to the real commands.
    • These folders are disposable: delete them and they can be regenerated.

    02 · Rules

    AGENTS.md

    One neutral file, five sections. Instructions are changed here and nowhere else.

    1. Description: who the agent works for and the current goals.
    2. Architecture: what each folder is for.
    3. Conventions: language, tone, note format.
    4. Constraints: search the notes before answering, read memory at session start.
    5. Prohibitions: folders that are never touched, nothing overwritten without approval.

    03 · Logic

    Commands

    Each command is a markdown file in commands/ that any agent can follow step by step.

    • Knowledge: /capture /ingest /update /inventaire /transcrire
    • Daily work: /morning /agenda /commit /bilan-objectifs
    • Teaching: /lecon42 /debug42 /expliquer42 /enonce42 /lecon-japonais

    Skills

    A skill is a folder of instructions loaded only when the task needs it. The rest of the time it costs no context.

    • Example: a news research skill, used by /morning.
    • Commands are also exposed as skill pointers in .agents/skills/ for agents that read that folder.
    • Rule: a skill that is not used is deleted, not disabled. In September 2026 the workspace held 120 installed skills, 3 of them in use: it was rebuilt around the few that serve.

    Sub-agents

    Smaller models take the bulk reading. They prepare, they never execute: the main agent and I decide.

    • Transcript reader (Sonnet): reads a large raw transcript and returns the ideas worth a note.
    • Committer (Haiku): reads a diff, looks for secrets, proposes a commit message.
    • SVG drawer (Sonnet): draws one diagram and writes only to a temporary folder.

    Scripts

    Anything that must give the same result every time is a script, not a prompt.

    • brain.mjs: keyword search across the vault.
    • prime.mjs: runs at session start and prints memory pointers and lessons due for review.
    • transcrire.py: turns a video source into a raw transcript.
    • banc.mjs: the evaluation bench.

    04 · Guardrails

    Permissions

    Three levels, written in a settings file and in AGENTS.md.

    • Runs without asking: vault search, git status, git diff, git log, Node and Python scripts.
    • Asks first: every file edit, every file write, git commit, git push.
    • Never: raw transcripts, my personal notes, the Obsidian configuration, the archive.

    Hooks

    A SessionStart hook runs prime.mjs when a session opens and after each context reset.

    • It prints the memory index, the size of the vault by domain and the lessons due for review.
    • The agent starts with pointers, not full files: it opens a note only when the task needs it.

    05 · Knowledge

    Second brain

    An Obsidian vault of plain markdown. Rule number one: the agent runs a search before any substantial answer, so it does not answer from memory on a topic already in the notes.

    • transcript/: raw sources, immutable.
    • wiki/: written entirely by the agent.
    • mes-notes/: written entirely by me, never modified by the agent.

    One note holds one idea, with YAML frontmatter and links to related notes. Every ingestion adds a line to a log. If two notes disagree, the most recent one wins and the gap is reported.

    Durable memory

    Facts that must survive between sessions: decisions, project status, working preferences.

    • One fact per note, in a folder under version control.
    • An index file is read at session start, the notes are opened when useful.
    • On an important change the agent proposes an update and writes it after approval.

    Dashboard

    A small Node.js server that scans the vault live and shows it as a graph in the browser. No build step, no database.

    06 · Measure

    Evaluation bench

    Built to measure a model swap instead of guessing.

    1. The tests live in one versioned file. The bench stores a SHA-256 fingerprint and refuses to run if the tests or the judge prompt changed since they were frozen.
    2. Each run happens in a disposable copy of the repository, inside a sandbox.
    3. Factual checks are done by script (which file changed, which command ran). Judgment checks go to a judge from another model family (Codex).
    4. Each test runs 5 times and every bench run writes a dated report.

    Two families of tests: signature tests check that a skill behaves as designed, canary tests are traps, such as a request to edit a protected file.

    Current limit: the bench still launches candidates through Claude Code and has not yet been run on a second harness, so there are no comparison figures to show.
